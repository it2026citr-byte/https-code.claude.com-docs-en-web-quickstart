# 03. Автоматизация тестирования: Vanessa Automation

Как превратить чек-лист из [02](02-test-checklist.md) в работающий регресс.

---

## 1. Пирамида тестов: что автоматизировать чем

Главная ошибка при автоматизации ERP — тащить всё в UI-сценарии Vanessa.
UI-тест ERP занимает 30–180 секунд; 181 автоматизируемая проверка в UI — это
2–8 часов прогона, который никто не будет ждать. Разделяем по уровням:

```
        ╱╲          E2E в UI (Vanessa)         ~30–40 сценариев   ← сквозные бизнес-процессы
       ╱  ╲         медленно, хрупко, дорого
      ╱────╲
     ╱      ╲       Проверка движений и данных  ~60–80 проверок   ← запросом после действия
    ╱        ╲      быстро, стабильно
   ╱──────────╲
  ╱            ╲    Модульные тесты кода        сколько нужно     ← общие модули, доработки
 ╱______________╲   мгновенно
 
 ─────────────────  Дымовые тесты               автоматически     ← открытие всех форм
```

| Уровень | Чем | Что берём из чек-листа |
|---|---|---|
| Дымовые | штатный модуль дымовых тестов VA | ПРФ-14, открытие форм, проверка на ошибки при открытии |
| Модульные | xUnitFor1C / АСТ (Автоматизированное сценарное тестирование) | доработки, общие модули, расчётные функции |
| Проверка данных | шаги VA с запросом к БД | ЦЕЛ-01…06, СКЛ-01…05, РЕГ-11/12, все «сходится/не сходится» |
| E2E UI | `.feature`-сценарии VA | ПРД, ЗАК, СКЛ, ПРЗ, КАЗ — сквозные цепочки |

**Практическое правило:** если проверку можно сформулировать как запрос
к регистрам — не пишите UI-сценарий, пишите проверку движений. UI нужен там,
где тестируется поведение формы: подстановки, доступность кнопок, статусы,
контроли.

## 2. Состав инструментария

| Компонент | Роль | Где взять |
|---|---|---|
| **Vanessa Automation** (`vanessa-automation.epf`) | движок BDD, библиотека шагов, запись сценариев | github.com/vanessa-automation/vanessa-automation |
| **vanessa-runner** (`vrunner`) | запуск из командной строки / CI | OneScript, `opm install vanessa-runner` |
| **OneScript** | среда для vrunner и вспомогательных скриптов | oscript.io |
| **coverage41C** | замер покрытия кода тестами | github.com/ci-for-1c/coverage41C |
| **Allure** | человекочитаемые отчёты о прогоне | VA умеет отдавать Allure/JUnit XML |
| **GitLab CI / Jenkins** | оркестрация прогонов | ваша инфраструктура |

Установка обвязки:

```bash
# OneScript уже установлен
opm install vanessa-runner
opm install vanessa-automation   # опционально, для получения .epf
```

обхода дерева: служебная подготовка должна идти первой.

## 4. Изоляция тестов — критично для ERP

UI-тесты ERP **меняют состояние базы**: остатки, нумерацию, взаиморасчёты,
закрытые периоды. Без сброса состояния второй прогон даст другой результат.

Три рабочих подхода, по возрастанию надёжности:

| Подход | Как | Плюсы / минусы |
|---|---|---|
| Уникальные данные | каждый сценарий создаёт свои объекты с уникальным префиксом (`АТ_<timestamp>_...`) | быстро, но база пухнет и остатки «плывут» |
| Снимок СУБД | MS SQL `DATABASE SNAPSHOT` / PostgreSQL база из шаблона — откат за секунды | быстро и надёжно, нужен доступ к СУБД |
| Восстановление из `.dt` | `1cv8 DESIGNER /RestoreIB эталон.dt` перед прогоном | максимально надёжно, но 10–60+ мин на ERP |

**Рекомендация для `erp_copy2`:** снимок на уровне СУБД перед прогоном +
уникальные префиксы внутри сценариев. Восстановление из `.dt` — только для
ночного полного регресса.

```cmd
:: tools/restore-test-db.cmd — пример для MS SQL
sqlcmd -S erpdevs -Q "RESTORE DATABASE erp_copy2 FROM DATABASE_SNAPSHOT = 'erp_copy2_snap_etalon';"
```

Дополнительно зафиксируйте детерминированность:

- **дата тестов** — все сценарии работают на фиксированной рабочей дате,
  не на `ТекущаяДата()`;
- **курсы валют** — загружены на весь тестовый период;
- **пользователь** — отдельный `АвтотестER`, с известным набором прав;
- **регламентные задания** — на время прогона отключены (иначе фоновое
  перепроведение испортит результат).

## 5. Соглашения по написанию сценариев

### Шапка файла

```gherkin
#language: ru
@tree
@Продажи
@P0

Функционал: Заказ клиента — полный цикл до отгрузки

Как менеджер по продажам
Я хочу оформить заказ клиента и отгрузить его
Чтобы проверить корректность резервирования, статусов и движений

Контекст:
	Дано Я открываю новый сеанс TestClient или подключаюсь к уже открытому
	И я закрываю все окна клиентского приложения
	И я установил рабочую дату "01.06.2025"
```

### Правила

1. **Один сценарий — одна проверяемая идея.** Не «продажи целиком», а
   «заказ резервирует товар», «отгрузка сверх заказа запрещена».
2. **Теги обязательны:** подсистема (`@Продажи`), приоритет (`@P0`),
   и ID проверки из чек-листа (`@ПРД-05`) — так отчёт о прогоне напрямую
   ложится на чек-лист.
3. **Проверять не только UI, но и движения.** Сценарий, который «нажал
   провести и не упал», не тестирует ничего. Всегда добавляйте проверку
   регистров.
4. **Никаких жёстких ссылок на конкретные элементы базы.** Нужный контрагент
   создаётся в подготовке или ищется по уникальному признаку.
5. **Ожидания вместо пауз.** `Я жду открытия окна "..." в течение 30 секунд`
   вместо `Пауза 5`. Иначе тест будет мигать.
6. **Именование по-русски**, как принято в 1С — читабельность для аналитиков
   важнее краткости.

### Свои шаги

Шаги проверки движений и подготовки данных выносятся во внешнюю обработку
`steps/ШагиТестированияERP.epf`. Минимально нужный набор:

```
Тогда движения документа "%1" по регистру "%2" содержат строку:
Тогда остаток по регистру "СвободныеОстатки" склад "%1" номенклатура "%2" равен %3
Тогда сумма проводок Дт "%1" Кт "%2" за период равна %3
Дано в базе есть контрагент с уникальным наименованием "%1"
Дано в базе есть номенклатура "%1" с остатком %2 на складе "%3"
Дано я запомнил ссылку на последний созданный документ как "%1"
Тогда в базе нет битых ссылок
```

Такие шаги окупаются мгновенно: один шаг «проверить движения» заменяет
десяток UI-проверок и не ломается от смены формы.

## 6. Параметры запуска

`tests/VAParams.json` — пример (состав ключей сверяйте со своей версией VA,
он менялся между релизами):

```json
{
  "ЗапускатьСценарии": true,
  "КаталогФайловFeature": "./tests/features",
  "КаталогИсходныхФайловБиблиотекиШагов": "./tests/steps",
  "ВыполнятьСценарииПоТегам": true,
  "СписокТеговДляВыполнения": "P0",
  "СписокТеговИсключение": "Черновик,Ручной",
  "ЗакрыватьTestClientПослеЗапускаСценариев": true,
  "ДелатьЗамерыПроизводительности": false,
  "ФорматОтчетаAllure": true,
  "КаталогOutputДляОтчетов": "./build/allure-results",
  "ЗавершатьРаботуСистемыПослеЗапускаСценариев": true
}
```

Запуск локально и в CI:

```bash
vrunner vanessa \
  --settings ./tests/VAParams.json \
  --ibconnection "/S erpdevs\erp_copy2" \
  --db-user "АвтотестERP" --db-pwd "***"
```

## 7. CI: ночной регресс

Пример GitLab CI. Логика та же для Jenkins.

```yaml
stages: [restore, smoke, regress, report]

variables:
  IB: "/S erpdevs\\erp_copy2_test"

restore_db:
  stage: restore
  script:
    - cmd /c tools\restore-test-db.cmd          # откат к эталонному снимку
  tags: [1c-runner]

smoke:
  stage: smoke
  script:
    - vrunner vanessa --settings tests/VAParams.smoke.json --ibconnection "%IB%"
  artifacts:
    when: always
    paths: [build/allure-results]

regress_p0:
  stage: regress
  needs: [smoke]
  script:
    - vrunner vanessa --settings tests/VAParams.json --ibconnection "%IB%"
  artifacts:
    when: always
    paths: [build/allure-results]
    reports:
      junit: build/junit/*.xml

allure_report:
  stage: report
  when: always
  script:
    - allure generate build/allure-results -o build/allure-report --clean
  artifacts:
    paths: [build/allure-report]
```

**Расписание:**

| Прогон | Когда | Состав | Целевое время |
|---|---|---|---|
| Дымовой | на каждое изменение конфигурации | открытие форм + 5–7 ключевых сценариев | ≤ 15 мин |
| P0-регресс | каждую ночь | все `@P0` | ≤ 2 ч |
| Полный | еженедельно / перед обновлением | `@P0 + @P1` + закрытие месяца | ≤ 8 ч |

## 8. Технические требования

- **Клиент тестирования.** VA работает через механизм TestManager/TestClient
  платформы. Нужны: свободный сеанс, отдельная лицензия, у пользователя —
  право `Тестирование` (или запуск клиента с ключом `/TESTMANAGER`).
- **Отдельная база.** Прогон должен идти на `erp_copy2_test`, а не на
  `erp_copy2`, если последняя используется для ручных проверок — параллельная
  работа человека и автотеста ломает обоих.
- **Машина-агент.** Толстый/тонкий клиент на агенте CI, GUI-сессия
  (для UI-тестов нужен рабочий стол — на Windows-агенте не через
  service-аккаунт без сессии).
- **Единая версия платформы** на агенте и на сервере.

## 9. Типичные грабли (и как их обойти)

| Симптом | Причина | Решение |
|---|---|---|
| Тест «мигает» — то проходит, то нет | гонка: сценарий не дождался открытия формы | шаги ожидания вместо пауз, увеличить таймаут |
| Второй прогон падает | не сброшено состояние базы | откат к снимку перед прогоном |
| Тест сломался после обновления ERP | привязка к заголовку элемента формы | привязываться к **имени** элемента (`с именем "ФормаПровести"`), а не к заголовку |
| Сценарий проходит, а баг в проде | проверялся только UI, не движения | добавить проверку регистров |
| Прогон идёт 6 часов | всё загнали в UI | перенести проверки данных на уровень запросов |
| Падает на закрытии месяца | не подготовлены НСИ/статьи расходов | вынести в подготовительный сценарий, проверять предусловия |
| Не находит элемент в веб-клиенте | различия отрисовки | фиксировать один клиент для регресса |
| Валится нумерация документов | параллельные прогоны на одной базе | одна база — один прогон |

## 10. Порядок внедрения

| Этап | Срок (ориентир) | Результат |
|---|---|---|
| 1. Инфраструктура: vrunner, агент, снимок базы, CI-джоб | 1 нед. | пустой прогон проходит в CI |
| 2. Дымовые тесты (открытие форм) | 3 дн. | ПРФ-14 закрыт, ловим падения форм |
| 3. Библиотека своих шагов (проверка движений, фикстуры) | 1 нед. | фундамент для всех сценариев |
| 4. 8–10 сценариев P0 по продажам и складу | 2 нед. | закрыт основной денежный поток |
| 5. Закупки, казначейство | 2 нед. | закрыт контур расчётов |
| 6. Производство, закрытие месяца | 2–3 нед. | закрыт учётный контур |
| 7. Права и RLS | 1 нед. | закрыт ПРВ |
| 8. Встраивание в регламент обновлений | — | регресс перед каждым обновлением |

Итого ориентировочно **2–2,5 месяца** до устойчивого ночного P0-регресса
силами одного инженера. Порядок и состав уточняются после
[сбора структуры базы](01-collect-db-structure.md).
